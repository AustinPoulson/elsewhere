## Shared coordination

Both runs use the same lock at `C:\repos\MAGI\elsewhere\.artifacts\automation-lock`, including when working in an isolated worktree. Acquire it atomically through exclusive creation before mutations; a check followed by an ordinary write is not a lock. Record the owning role, run identity, acquisition time, card, branch/worktree, and relevant revisions. Planning holds it for board mutations; execution holds it for claims and development/publication. If another run owns it or ownership is unclear, defer mutations. Remove a stale lock only after confirming its prior run is inactive; release only the lock owned by the current run. Read-only planning can continue without the lock.

Inspect active runs, claimed cards, local branches/worktrees, and open PRs as well. Mirror the owner, claim, and recovery state in the Direction list's charter/coordination record for visibility; this Trello note is not the exclusion mechanism. Recheck lock ownership and the card immediately before changes. The schedules and a claim's age do not authorize takeover. Never rewrite a claimed ticket's scope.

## Weekly planner

At Monday 8 AM, inspect the code, live experience, expedition evidence, all open PRs, incomplete work, and board. Research only where it answers a concrete artistic or technical question. Maintain one coherent four-to-six-week direction and a next-week focus on the Direction card. Curate the queue using the [planning contract](planning.md): deduplicate, narrow, order, document dependencies, and retire obsolete unclaimed cards to Deferred/Canceled or recoverable archives with reasons rather than deleting them. Aim for three to seven well-scoped Ready cards; quality takes precedence over filling a quota. Top Ready is first to execute. Protect active work and defer incompatible new direction until its handoff is resolved.

Planning changes direction and tickets, not production code, repository commits, or deployments. Report meaningful direction/queue changes or blockers; stay quiet when nothing substantive changes.

An unresolved deployment or required live-acceptance check blocks unrelated new implementation. If resolving it requires code or a safe verification fixture, the planner may prioritize one specifically linked recovery ticket in Ready. Its scope must identify the blocked card/revision, the repair, and evidence that resolves the blocker. The executor may implement only that repair until verification is recovered; otherwise it records Blocked and stops implementation. The recovery ticket passes the same review, test, deployment, and live-acceptance gates, and does not silently waive the original card's acceptance.

## Daily executor

1. **Recover and inspect.** Confirm the standalone `AustinPoulson/elsewhere` remote, `main`, board URL/list names, and shared lock ownership. Preserve unrelated local changes. Reconcile In Progress/Blocked cards, branches, every open PR, and prior run evidence. Resume actionable unfinished work first. A merged or deployed ticket lacking required verification blocks unrelated new implementation: verify or repair it first, or execute only the planner's explicitly linked Ready recovery ticket under the exception above. Without an actionable repair, record Blocked and stop implementation.
2. **Claim one ticket.** When recovery does not restrict the run, take the top unblocked Ready card whose dependencies are satisfied; during recovery, claim only the specifically linked repair. Re-read it and the board before moving it to In Progress. Record its acceptance contract, branch/worktree, and claim while holding the lock. If no executable Ready card or recoverable work exists, leave the queue and repository unchanged and stay quiet.
3. **Implement its scope.** Start a fresh `codex/` branch from current `main` in an isolated Elsewhere worktree or clean standalone checkout. Resume an unmerged branch for unfinished work; a repair after merge needs a new branch and PR. Delegate narrow work where useful. Make routine technical choices within the ticket's visible effect and constraints. Do not invent a different feature. Record unclear acceptance or missing dependencies on the card, move it to Blocked with the precise unblock condition, and preserve work. Out-of-scope discoveries become Ideas proposals, not bundled changes.
4. **Validate and play.** Run `npm ci` and `npm run validate`; preserve existing checks and add meaningful behavior/regression tests. Exercise applicable resource budgets, deterministic continuation, existing autosaves, portable snapshots, and any migration. Inspect the rendered addition on desktop and portrait; verify the visible relationship, keyboard/focus, reduced motion, pause/reset, and affected save paths. Use an isolated disposable test world for live QA; do not reset/import over a personal world without specific authorization. A valid resource-limited refusal is not evidence of a positive interaction. Record screenshots, real-device limits, and acceptance results on the card and expedition note.
5. **Review the PR.** Commit/push only the passing candidate to its feature branch and open a PR against `main`, linking the ticket both ways. Review the complete final remote diff; verify intended deletions/renames as well as additions and record head/base SHAs. Wait for CI on that final head and GitHub's tested integration result. If either revision changes, review again and repeat affected validation and browser checks. Branch/PR workflows do not deploy.
6. **Merge and deploy.** Recheck head and base immediately before merging; merge only the reviewed, passing head SHA through its PR. Record GitHub's merged commit SHA. Never push scheduled additions directly to `main`. Main's Pages workflow validates and then deploys; manual dispatch on `main` can redeploy an already reviewed revision.
7. **Verify and finish.** Wait for that merged revision's workflow/deployment success. Fetch the live `release.json` without a cached response and require its `commit` to equal the merged SHA. Inspect the live addition, interactions, and assets. Only then move the card to Completed, attach the PR, workflow, deployed SHA, live URL, and acceptance evidence, and report completion. If publication occurred but verification did not, record that exact recovery state and keep the card unfinished.

## Access and failure

Use existing authenticated local Git and verify access each run. The authenticated GitHub browser is a fallback when CLI/connector writes are unavailable; compare its complete remote tree/diff with the validated candidate before merge. Browser uploads must include deletions and renames. Do not expand account permissions to bypass access limitations. For this checkout's known Windows ownership mismatch, scope any exception to `git -c safe.directory=C:/repos/MAGI/elsewhere`; do not change global trust settings.

Failed checks, conflicts, inaccessible dependencies, or deployment verification stop advancement. Repair the current ticket when feasible; otherwise preserve its branch and evidence, record the failed stage/unblock condition, and leave it Blocked or In Progress as appropriate. If automatic approval review rejects an action, record the action, stated reason, and specific required Operator step; do not attempt a workaround. Never weaken tests or call an unverified deployment Completed. Use `in_progress` while working, `completed` for finished implementation, `blocked` for a concrete dependency, and `verified` for an accepted live result. Notify only on substantive planning changes, verified completion, failures, or needed Operator input.
