[Planning and board contracts](planning.md) define their handoff.

## Weekly planner

At Monday 8 AM, inspect the code, live experience, expedition evidence, all open PRs, incomplete work, and board. Research only where it answers a concrete artistic or technical question. Maintain one coherent four-to-six-week direction and a next-week focus on the Direction card. Curate the queue using the [planning contract](planning.md): deduplicate, narrow, order, document dependencies, and retire obsolete unclaimed cards to Deferred/Canceled or recoverable archives with reasons rather than deleting them. Prepare nine to ten outcome-oriented feature Ready cards for seven daily runs plus two or three independently eligible alternatives, and maintain fifteen to twenty-five structured future Ideas when justified. Do not add filler to reach a count. Every Ready card must add a meaningful new playable capability, such as a creature, action, behavior, weather system, or control that interacts with the ecosystem; isolated readout/cue polish and bug fixes do not qualify as the day's feature. Top Ready is first to execute. Protect active work and defer incompatible new direction until its handoff is resolved.

Planning changes direction and tickets, not production code, repository commits, or deployments. Cover seven daily slots plus two or three independently eligible alternatives, normally nine to ten Ready features. Account for unfinished work and dependency chains; Ideas and blocked cards do not count as actionable weekly coverage. Report meaningful direction/queue changes or blockers; stay quiet when nothing substantive changes.

Plan outcomes and hard guardrails rather than exhaustive designs. Execution has creative ownership of mechanics, tuning, visual expression, animation, sound, naming, UI flow and implementation choices within the intended capability. Detailed suggestions, including existing card prescriptions, are starting points unless necessary to an explicitly identified invariant. Prototype and play-test those choices, document material decisions, and seek a handoff only for a changed objective, hard invariant/dependency, material expansion or unresolved feasibility/safety issue. An aesthetic or tuning choice is not a blocker.

Feature-first planning resolves concrete design decisions so complete creature lifecycles and other core systems can reach Ready as satisfying vertical slices. Do not split a meaningful feature into weeks of minor cue polish, or indefinitely park it because its design needs thought. Choose the decisions, resource rules, and migration policy that make a bounded slice executable; unresolved feasibility stays in Ideas with the specific next evidence needed.

Track routine defects as linked side-work cards with their own evidence and priority. Nonblocking historical QA gaps, tooling limitations, and unrelated defects do not freeze new feature development. Classify a true release blocker by concrete evidence: save loss, a security risk, failed required checks, or failure of the candidate's required publication/live acceptance. Repair those before publishing the affected candidate, then continue its feature in the same run when feasible. Never waive acceptance or publish a failed candidate. A bug-only recovery day is recorded honestly as recovery, not as delivery of the daily feature.

## Daily executor

1. **Inspect and classify.** Confirm the standalone `AustinPoulson/elsewhere` remote, `main`, board URL/list names, and shared lock ownership. Preserve unrelated local changes. Reconcile In Progress/Blocked cards, branches, every open PR, and prior run evidence. Resume actionable unfinished feature work first. Distinguish true release blockers from nonblocking old QA/tooling gaps; keep the latter traceable without letting them freeze unrelated feature development. Resolve safety and failed-check blockers before publishing the affected candidate.
2. **Claim a daily feature.** Take the top eligible feature Ready card whose dependencies are satisfied, or resume the already claimed feature. Re-read its complete contract and the board before moving it to In Progress. Record its meaningful new capability, playable before/after demonstration, branch/worktree, and claim while holding the lock. Target one significant new feature each day. Routine defects are side work, not a substitute headline; if no executable feature exists, record that queue gap without inventing a feature or promoting Ideas.
3. **Implement its scope and necessary repairs.** Start a fresh `codex/` branch from current `main` in an isolated Elsewhere worktree or clean standalone checkout. Resume an unmerged branch for unfinished work; a repair after merge needs a new branch and PR. Delegate narrow work where useful. Make creative and technical choices within the ticket's intended capability and mandatory guardrails; prototype and tune suggested details without a planning round. Link scoped bug fixes and their evidence; include a fix in the feature PR only when necessary for that feature, otherwise use a separate branch/PR. Resolve true blockers and continue the feature in the same run when feasible. Do not invent a different feature or bundle unrelated changes. Record unclear acceptance or missing dependencies on the card, move it to Blocked with the precise unblock condition, and preserve work; another eligible feature may proceed only without overlapping claims/publication or rewriting the blocked contract. Out-of-scope discoveries become Ideas proposals.
4. **Validate and play.** Run `npm ci` and `npm run validate`; preserve existing checks and add meaningful behavior/regression tests. Exercise applicable resource budgets, deterministic continuation, existing autosaves, portable snapshots, and any migration. Inspect the rendered addition on desktop and portrait; verify the visible relationship, keyboard/focus, reduced motion, pause/reset, and affected save paths. Use an isolated disposable test world for live QA; do not reset/import over a personal world without specific authorization. A valid resource-limited refusal is not evidence of a positive interaction. Record screenshots, real-device limits, and acceptance results on the card and expedition note.
5. **Review the PR.** Commit/push only the passing candidate to its feature branch and open a PR against `main`, linking the ticket both ways. Review the complete final remote diff; verify intended deletions/renames as well as additions and record head/base SHAs. Wait for CI on that final head and GitHub's tested integration result. If either revision changes, review again and repeat affected validation and browser checks. Branch/PR workflows do not deploy.
6. **Merge and deploy.** Recheck head and base immediately before merging; merge only the reviewed, passing head SHA through its PR. Record GitHub's merged commit SHA. Never push scheduled additions directly to `main`. Main's Pages workflow validates and then deploys; manual dispatch on `main` can redeploy an already reviewed revision.
7. **Verify and finish.** Wait for that merged revision's workflow/deployment success. Fetch the live `release.json` without a cached response and require its `commit` to equal the merged SHA. Inspect the live addition, interactions, and assets. Only then move the card to Completed, attach the PR, workflow, deployed SHA, live URL, and acceptance evidence, and report completion. If publication occurred but verification did not, record that exact recovery state and keep the card unfinished.

## Access and failure

Use existing authenticated local Git and verify access each run. The authenticated GitHub browser is a fallback when CLI/connector writes are unavailable; compare its complete remote tree/diff with the validated candidate before merge. Browser uploads must include deletions and renames. Do not expand account permissions to bypass access limitations. For this checkout's known Windows ownership mismatch, scope any exception to `git -c safe.directory=C:/repos/MAGI/elsewhere`; do not change global trust settings.

Failed required checks, unsafe saves, conflicts, inaccessible dependencies, or failed candidate deployment/live acceptance stop publication of that candidate. Repair the current feature when feasible and continue its upgrade; nonblocking historical QA or tooling gaps are not blanket feature freezes. Never mark a bug-only day as a completed daily feature. If repair cannot complete, preserve its branch and evidence, record the failed stage/unblock condition, and leave it Blocked or In Progress as appropriate. If automatic approval review rejects an action, record the action, stated reason, and specific required Operator step; do not attempt a workaround. Never weaken tests or call an unverified deployment Completed. Use `in_progress` while working, `completed` for finished implementation, `blocked` for a concrete dependency, and `verified` for an accepted live result. Notify only on substantive planning changes, verified completion, failures, or needed Operator input.
